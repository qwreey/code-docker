# code-docker 도움말/가이드 임베드 (아이디어 단계 — 구현 안 함, 질문만 정리)

> **이 문서는 구현하지 않는다.** 사용자가 "지금 작업은 하지 말고 읽어보고 생각해볼게"라고
> 명시적으로 요청 — 아래는 아이디어 스케치 + 구현 시작 전에 사용자가 결정해줘야 할
> 질문 목록. 우선순위도 아직 미정(다른 `*-plan.md`들과 달리 큐에 넣지 않음).

## 동기

지금 `README.md` 하나가 전부(설정법, override 시스템, 통합별 tips, webmanager 기능
목록 등)를 담고 있는데, 계속 커지면서 사람이 한 파일로 훑어보기 점점 힘들어지고
있음. 언젠가 여러 페이지로 쪼개고, 정리하고, 이미지도 넣는 식으로 손보게 될 텐데 —
그 참에 이 내용을 webmanager 안에도 "도움말/가이드" 형태로 임베드해서, 컨테이너를
직접 쓰는 사람이 GitHub까지 안 나가도 브라우저 안에서 바로 참고할 수 있게 하면
어떨까 하는 아이디어.

## 이 문서가 다루는 범위

지금 당장 뭘 만들지가 아니라, **나중에 실제로 착수할 때 막히지 않게 미리 정해둬야
할 질문들**을 모으는 것. 아래 "결정 필요" 절이 이 문서의 핵심.

## 대략적인 그림 (검증 안 된 초안)

- `README.md`를 여러 개의 마크다운 파일로 쪼갬 (예: `docs/*.md` 같은 새 디렉토리 —
  정확한 위치/구조는 "결정 필요" 참고).
- webmanager 프론트엔드에 새 탭(가칭 "가이드" 또는 "도움말") 추가, 그 마크다운
  파일들을 렌더링해서 보여줌.
- GitHub에서도 그대로 읽혀야 하니(이 레포를 처음 보는 사람은 여전히 GitHub에서
  README/docs를 읽음), **같은 마크다운 파일을 두 군데(GitHub 웹, webmanager)가
  공유**하는 쪽이 자연스러워 보임 — 내용을 따로 관리/복제하지 않도록.
- 이미지도 넣을 수 있어야 함 (지금 README는 텍스트뿐).

## 결정 필요 (구현 착수 전에 답이 있어야 함)

1. **탭 이름/작명**: "가이드"? "도움말"? "문서"? "Docs"? — sidebar `SECTIONS`에
   들어갈 라벨과 이 문서/기능 자체의 이름(현재 파일명은 일단 `guide-plan.md`로
   뒀는데, 나중에 바꿔도 비용 거의 없음).
2. **문서 파일들이 실제로 어디 사는가**:
   - 저장소 루트에 새 `docs/` 디렉토리를 만들고 `README.md`는 짧은 인덱스/소개로
     남긴 뒤 나머지를 그쪽으로 옮기는 구조? 아니면 다른 위치?
   - webmanager가 이 파일들을 **빌드 시점에 정적 자산으로 번들**(예: Vite의
     `?raw` import, 또는 프론트엔드 빌드 스크립트가 `docs/`를 복사)하는 방식과,
     **런타임에 컨테이너 안에서 읽어오는** 방식(override 패턴처럼 `/etc/code-docker`
     경유 또는 백엔드가 직접 리포 경로를 읽음) 중 어느 쪽? 전자는 이 레포의 기존
     "webmanager 정적 프론트엔드는 빌드 시점에 굳는다"는 관례와 맞고, 후자는
     "override 파일은 리빌드 없이 반영"이라는 다른 관례와 맞음 — 이 문서는 둘 다
     후보로 남겨두고 확정 안 함.
3. **문서를 override 가능하게 할지**: 이 프로젝트를 fork해서 자기 조직용으로
   커스터마이징하는 사람이 이 도움말 내용도 자기 것으로 바꾸고 싶어할 수 있음
   (`config/*.override.*` 관례와 동일한 결). 아니면 이건 "code-docker 자체에 대한
   설명"이라 원본 그대로 유지하는 게 맞고, 조직별 커스터마이징은 범위 밖으로 볼지도
   결정 필요.
4. **마크다운 렌더링 방식**: 프론트엔드가 실제 CommonMark를 다 지원하는 라이브러리
   (`react-markdown`, `markdown-it` 등)를 새 의존성으로 들일지, 아니면 이 문서들이
   어차피 우리가 직접 쓰는 통제된 콘텐츠니까 필요한 문법(제목/코드블록/표/링크/이미지
   정도)만 지원하는 가벼운 자체 파서로 충분한지. 참고로 이 저장소는 다른 곳(Claude
   Code M2 차트, 리소스 히스토리 그래프)에서 "차트 라이브러리 새로 안 들이고 직접
   SVG로 구현"하는 걸 일관되게 선택해왔음 — 같은 결을 마크다운 렌더링에도 적용할지,
   아니면 마크다운 파싱은 차트와 성격이 달라서(범용 문법을 정확히 구현하는 게 더
   중요) 예외로 라이브러리를 허용할지 판단 필요.
5. **이미지 저장 위치/관례**: `docs/assets/` 같은 디렉토리 컨벤션을 새로 정할지.
   실제 실행 중인 webmanager UI 스크린샷을 넣을 경우 UI가 바뀔 때마다 스크린샷도
   같이 갱신해야 하는 유지보수 부담이 생기는데, 그 정도 부담을 감수할지 아니면
   다이어그램/개념도 위주로만 쓸지.
6. **탭 내부 네비게이션**: 페이지가 여러 개로 늘어날 텐데, sidebar `SECTIONS`에
   페이지마다 항목을 하나씩 추가하면 금방 sidebar가 도움말 페이지들로 뒤덮일 것 —
   대신 "가이드" 탭 하나 아래에 자체적인 목차/서브 네비게이션(탭 안의 사이드 메뉴,
   또는 상단 페이지 선택 드롭다운)을 두는 쪽이 나아 보이는데 이 구조로 확정해도
   되는지.
7. **분할/재구성 작업 자체를 누가 하는가**: `README.md`를 실제로 여러 파일로
   쪼개고 다듬는 작업 — 나중에 착수할 때 Claude(서브에이전트 활용 가능)에게
   맡길지, 사용자가 직접 손으로 재구성한 뒤 webmanager 렌더링 부분만 Claude가
   만들지.
8. **검색**: 페이지가 늘어나면 탭 안에서 검색이 있으면 좋을 텐데, 1단계 범위에
   넣을지 나중 개선사항으로 미룰지 (정적 콘텐츠라 클라이언트 사이드 전문 검색으로
   충분해 보이지만, 이것도 나중 이야기).

## 참고

- 우선순위/큐 배치는 위 질문들에 답이 나온 뒤 `webmanager/plan.md`/`CLAUDE.md`에
  반영.
- `webmanager/ideas.md`에 이미 있던 "VS Code / code-server 설정 UI" 후순위 판단과
  비슷하게, 이 기능도 "쓸모는 있지만 지금 급하지 않다"는 카테고리 — 급하게 결정할
  필요는 없음.
