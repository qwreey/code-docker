# 모바일 한글(IME) 입력 파손 — 조사 기록 + 다음 계획

작성 2026-09-03. **착수 전. 시도했던 수정은 되돌려놨음(작업 트리 클린).**
실사용 회귀이고 사용자가 매일 겪는 문제지만, 파고 보니 안드로이드 IME 동작에
의존하는 부분이 많아 추측만으로는 더 못 간다고 판단해 백로그로 내림.

## 증상

webmanager 터미널 탭에서 한글이 자모 단위로 쪼개져 입력됨 — `한글` → `ㅎㅏㄴㄱㅡㄹ`,
`가나다` → `ㄱㅏㄴㅏㄷㅏ`. 갤럭시 태블릿(북커버 물리 키보드)과 갤럭시 폰(가상 키보드)
**둘 다** 재현. 물리 키보드도 삼성 IME를 거치므로 같은 경로다.
일반 브라우저 탭과 설치된 PWA 창 **모두 동일**(→ PWA display-mode는 무관, 배제).
옛날 프로덕션 배포본은 멀쩡.

## 확정된 사실

- **워크어라운드를 끄고 페이지 새로고침하면 정상 동작한다** (사용자 확인).
  이때 xterm 쪽에서는 조합 중인 부분이 검은색 표시로 보인다 —
  즉 **xterm의 textarea에서는 조합이 실제로 일어난다.**
- 따라서 문제는 `Terminal.tsx:721-878`의 모바일 입력 워크어라운드가 만드는
  전용 입력 필드 쪽이고, **그 필드에서는 `compositionstart`가 아예 안 뜬다.**
  `composing`이 계속 `false`라 `onInput`(838-841행)의 early-return이 안 걸리고
  매 자모가 즉시 `sendBytes`된다. 리셋이든 포커스든 전부 그 다음 문제다.
- **`autocorrect="off"`/`spellcheck="false"`는 범인이 아니다.** 같은 코드가
  xterm의 textarea에도 똑같이 걸어두는데(`Terminal.tsx:689-694`) 그쪽은 조합이 된다.
- **xterm 버전 회귀 아님.** `9a37373..HEAD`에서 `package.json`/`package-lock.json`
  diff 0, `@xterm/xterm` 6.0.0 고정.
- **배제됨**: cwd 폴링(`setSessions`만 부르고 컨테이너 언마운트 없음, 생성 이펙트 deps `[]`),
  모드키 바(명시적 `onClick`에서만 `focusTerminal()`, 매 touchend 재포커스는
  `60f556f`에서 오히려 제거됨), 백엔드(`handlers_terminal.go:176-179`가
  WS 프레임을 `ptmx.Write`로 그대로 씀), `d624ef1`/`51a1339`.

## 왜 예전엔 멀쩡했나 (회귀 경위)

`sendBytes`(`Terminal.tsx:501-514`)가 매 전송마다 `focusTerminal()`을 부르는데,
`60f556f`(2026-08-21) **이전**의 `focusTerminal()`은 `XTerm.focus()`를 불러
포커스를 **xterm의 진짜 textarea로 보냈다.** 즉 첫 키 입력 이후 실제 입력이
워크어라운드 필드가 아니라 네이티브 textarea로 흘렀고, 그래서 한글이 정상
조합됐다. `60f556f`의 커밋 주석이 이걸 반대편에서 기술한다 — "툴바 버튼 한 번
누르면 그 타이핑 세션 내내 예측입력 버퍼링 버그가 되살아났다." **그 '되살아난
버그'가 네이티브 IME가 정상 동작하던 상태였다.** `60f556f`가 그 우발적 탈출구를
막으면서 워크어라운드가 설계대로 동작하기 시작했고, 한글이 깨졌다.

## 워크어라운드가 원래 잡으려던 버그 (사용자 설명)

xterm 네이티브 경로에서 **`가나다라` 입력 후 스페이스 → `가나다라가나다라` 중복**.
이게 원래 문제였다. xterm.js의 `CompositionHelper`가 안드로이드 IME와 맞물릴 때
조합 텍스트를 두 번 흘리는 것으로 보인다.

워크어라운드는 두 개의 독립적인 장치로 이뤄져 있다:

- `type="password"` — 예측/조합 억제 (한글 파손의 원인)
- ANCHOR 리셋 — 입력창을 항상 한 글자로 유지해 IME가 이미 PTY로 보낸 앞부분까지
  되돌아가 고치는 것을 방지

## 시도했다가 되돌린 것 (2026-09-03)

`type="password"` → `'text'` + `scheduleReset`에 `if (composing) return` 가드.
빌드/린트/기동은 통과했으나 **실기기에서 증상 동일** — 여전히 `ㄱㅏㄴㅏㄷㅏ`.
`type`만 바꿔서는 이 필드에 조합이 붙지 않는다. 전부 revert함.

(참고: 그 전에 검토했던 "`focusTerminal()`이 이미 activeElement면 생략" 가드는
**적용하면 안 된다** — 포커스를 워크어라운드 필드에 고정시켜 깨진 상태를 굳힌다.)

## 남은 가설 (미검증)

`type="text"`로도 조합이 안 붙는 이유로 남은 실질적 차이:

1. **`<input>` vs `<textarea>`** — xterm의 helper는 textarea이고 거기선 조합이 된다.
   안드로이드에서 단일행 input과 다중행 textarea는 IME 입력 타입이 다르게 잡힌다.
   **현재 가장 유력.**
2. ANCHOR(`value = ' '`) + `setSelectionRange`가 조합 시작을 방해할 가능성
3. `aria-hidden="true"` / `tabIndex = -1`

## 다음 계획

**1단계 — 계측 먼저.** 기기 동작을 두 번 틀렸으므로 세 번째 추측보다 실측이 낫다.
터미널 설정 패널에 "입력 디버그" 토글(localStorage, 다른 실험적 토글과 동일 관례)을
넣어 마지막 이벤트 N개를 화면 구석에 표시한다: 이벤트 `type`, `isComposing`,
필드 값, 실제로 보낸 바이트. 갤럭시에서 무슨 이벤트가 오는지 확정한 뒤 고친다.

**2단계 — 구조 변경.** 지금 설계는 입력창을 한 글자로 잘라 IME와 싸우는 방식인데,
버퍼를 쌓게 두고 diff로 처리하는 쪽으로 바꾼다 (사용자 제안 방향):

- 필드를 `<textarea>`로 (xterm helper textarea와 동일 스타일/속성). 단 xterm의
  `CompositionHelper`는 계속 우회 — `가나다라가나다라` 중복이 거기서 나오므로
- ANCHOR/리셋을 버리고 **공통 접두사 diff**: `sent`(이미 PTY로 보낸 문자열)와 현재
  값의 공통 접두사를 구해 줄어든 만큼 `\x7f`, 늘어난 만큼 새 텍스트를 보낸다.
  IME가 앞부분을 되돌아가 고쳐도 diff가 자연히 처리하므로 필드를 잘라둘 이유가
  없어진다. 백스페이스도 필드에 내용이 있어 그냥 동작한다(ANCHOR가 있던 이유)
- 조합 중엔 아무것도 안 보내고 `compositionend`에서만 diff를 흘린다
- `sendBytes`의 `focusTerminal()` 호출 제거 — 데이터를 만든 엘리먼트는 정의상 이미
  포커스를 갖고 있어 불필요하고 IME에 적대적이다. 툴바 버튼 경로의 호출은 유지
- 필드가 무한정 자라지 않게, 조합이 없고 입력이 잠잠할 때만 잘라낸다

**폴백.** 위가 안 되면 워크어라운드 기본값을 OFF로 돌린다
(`loadMobileInputWorkaroundEnabled()`의 `!== '0'` → `=== '1'`, 한 줄).
지금은 `pointer: coarse`인 **모든** 기기가 기본으로 이 경로를 타므로 모든 CJK
사용자가 이 버그를 겪는다. 한글 완전 파손 vs 라틴 예측 버퍼링 불편은 비교 대상이
아니다. `TerminalSettingsPanel.tsx:255-271`의 설명 문구에도 IME 파손을 명시할 것.

## 남겨둘 것

`Terminal.tsx:829-833`의 주석이 "password 필드가 composition을 억제하지 않는다"고
**명시적으로 틀리게 단언**하고 있다. 이 버그가 2주간 안 드러난 이유이기도 하니,
어떤 방향으로 고치든 이 주석은 반드시 정정할 것.
