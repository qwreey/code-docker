# 활성 세션 목록 보기 (대체됨 — heartbeat 방식으로 구현 완료, 아카이브)

> **대체됨 — 실제 구현은 `session-heartbeat-plan-done.md`(같은 폴더) 참고,
> 실사용 검증까지 완료됨.** 사용자가 아래 옵션 1~4 중 아무것도 고르지 않고,
> 클라이언트가 UUID를 자체 발급해 주기적으로 heartbeat를 쏘는 5번째 방식으로
> 스코프를 직접 확정함 — 옵션 2(code-server 자체 연결 API)의 "실현 가능한지부터
> 불확실" 문제를 통째로 우회하는 방식이라, 이 문서가 요구했던 "사용자와
> 인터랙티브 확인"은 완료된 것으로 간주. 이 문서는 옵션 2(및 1, 3, 4)가 여전히
> 조사되지 않았다는 기록 용도로만 남겨둠 — 나중에 "code-server 자체 연결
> 목록"이 별도로 필요해지면 그때 참고.

## 동기 (사용자 설명 그대로)

지금 브라우저로 code-docker/webmanager에 접속해있는 세션들의 목록을 보고
싶음 — "어디에 뭘 켜놨는지" 알고 싶은 것. 보안 목적이라기보다 **가시성/편의
목적**에 가까움: 이미 앞단에 Authentik 같은 SSO가 있으니, 진짜 보안상 세션을
끊어야 할 상황이면 거기서 처리하면 됨(webmanager가 그 역할을 대신할 필요
없음) — 이 기능은 "지금 뭐가 켜져 있는지 한눈에 보기"가 핵심.

## 무엇을 만들지부터 불명확함 (착수 전 사용자와 반드시 확인)

"세션"이라는 단어가 가리킬 수 있는 게 최소 4가지고, 각각 기술적 실현
가능성/난이도가 완전히 다름 — 아래 조사 결과를 사용자에게 보여주고 어떤
조합을 원하는지 확인부터 해야 함:

1. **webmanager 자체의 비밀번호 게이트 세션** (`internal/authgate`) — 가장
   실현 가능성 높음. 이미 `sessionStore`가 발급된 토큰과 만료 시각을
   인메모리로 들고 있음(`internal/authgate/session.go`) — 지금은
   토큰→만료시각만 저장하지만, 발급 시점에 IP/User-Agent/발급 시각 정도를
   같이 저장하도록 확장하면 "지금 누가 잠금을 풀어놓은 상태인지" 목록을 만드는
   건 어렵지 않음. **단, 이건 비밀번호 게이트를 설정해서 쓰고 있을 때만 의미가
   있는 개념** — 게이트 자체가 꺼져 있으면(기본 상태) "세션"이라는 개념이 아예
   없음(리버스 프록시 인증에만 의존하므로 webmanager 입장에서는 익명 요청과
   구분 불가).
2. **code-server 자신의 연결/세션** — 실현 가능성 **불확실**. code-server가
   업스트림 VS Code Server를 그대로 쓰는데, "지금 연결된 브라우저 탭/클라이언트
   목록"을 조회할 수 있는 공식 API/CLI가 있는지 확인 안 됨(VS Code Server
   내부 구현이라 문서화가 안 돼있을 가능성이 있음, 조사 필요). 사용자가
   실제로 가장 궁금해하는 게 이것일 가능성이 높아 보임("code-server를 여러
   기기/탭에서 열어뒀을 때 그 목록") — 근데 정작 가장 조사가 안 된 부분.
3. **리버스 프록시/Authentik 세션** — webmanager 범위 완전히 밖. Authentik
   자신의 API를 통합해야 하는데(새 인증정보/API 키 필요, webmanager가 지금까지
   외부 SSO 시스템과 통합한 적이 전혀 없음), 이건 사실상 "webmanager가
   Authentik 관리 콘솔의 일부 기능을 흉내내는" 새로운 통합 프로젝트에 가까움 —
   사용자 본인이 "Authentik 가서 세션 갈면 된다"고 이미 언급해서, Authentik
   자체를 대체하려는 의도는 아닌 것으로 보임(그래도 "읽기 전용으로 보여주기"
   정도는 원할 수도 있음, 확인 필요).
4. **날 것의 TCP 연결 목록** (`/proc/net/tcp`에서 80/81/22 포트로의 established
   연결) — 기술적으로는 당장 가능(이미 Processes 탭에 비슷한 걸 하는
   `internal/procinfo`가 있음). 근데 "브라우저 세션"의 좋은 대리 지표가 아님 —
   HTTP keep-alive/커넥션 풀링 때문에 연결 수와 실제 열려있는 탭 수가 일치
   안 할 가능성이 높고, 사용자가 실제로 원하는 "무엇을 열어뒀는지"라는 질문에
   제대로 답을 못 줌. 참고용으로만 언급, 이것만으로 이 기능을 만드는 건
   비권장.

## 착수 시 반드시 할 일

1. **사용자에게 위 1~4번 중 뭘 원하는지 (또는 조합인지) 먼저 확인** — 특히
   2번(code-server 자체 세션)이 실제로 가능한지부터 조사하고, 안 되면 대안
   (1번만 제공? 4번을 보조 지표로 곁들일지?)을 사용자와 상의.
2. 2번이 가능하다고 밝혀지면, 정확히 뭘 보여줄 수 있는지(기기/브라우저
   식별자? 마지막 활동 시각? 강제 종료 가능 여부?)도 다시 조사해서 사용자와
   맞춰볼 것.
3. 1번(webmanager 게이트 세션)만이라도 원하면 비교적 빠르게 구현 가능 —
   `internal/authgate`의 `sessionStore`에 메타데이터 필드 추가 + 목록 조회
   엔드포인트만 있으면 됨(비밀번호 게이트 자체를 관리하는 기능이라 이것도
   게이트 대상으로 두는 게 맞아 보임).
