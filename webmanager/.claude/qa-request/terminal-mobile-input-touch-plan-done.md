`research/mobile-ime-hangul-plan.md`(2026-09-03 조사)를 대체한다 — 그 문서의 "다음 계획"

## 사용자 제보 (2026-09-06)

이전 조사 때와 **증상이 달랐다.** 그때는 자모 분리(`ㄱㅏㄴㅏㄷㅏ`)였는데 이번엔
중복(`가나다. 가나다. 가나다`)이다. 결정적인 새 실측 세 가지:

- 터미널 **바깥을 터치했다가 다시 터미널을 터치하면** 잠시 정상으로 돌아온다.
  키보드가 닫히지도 않는다. 그리고 다시 문제가 생기면 "고쳐졌던 지점 이후로"
  다시 복제가 시작된다.
- `안녕 나는`을 쓰고 `나는`을 지우면 **`안녕`에 대한 자동완성 후보가 뜬다.**
  바깥을 탭했다 돌아오면 그 후보가 사라진다.
- 즉 삼성 입력기가 **이전 버퍼를 들고 있다가 조건이 맞으면 다시 흘려보낸다**는
  사용자 가설. 코드 쪽에서 보이는 그림과 정확히 맞는다.

## 무엇을 고쳤나

### 1. 입력 방식이 이제 3종 선택 (`TerminalInputMode`)

기존엔 "모바일 입력 워크어라운드" 체크박스 하나(켬=password 필드, 끔=xterm 기본)
였다. 어느 쪽도 옳지 않다는 게 두 번의 실측으로 드러났으므로, 세 번째 방식을 만들고
셋 다 고를 수 있게 했다. `localStorage`의 `webmanager.terminal.inputMode`.

| 값 | 동작 | 알려진 증상 |
|---|---|---|
| `native` | xterm 자체 textarea | 예측 버퍼링 + **중복 입력** |
| `password` | 기존 `<input type="password">` | 예측 완전 차단, **한글 자모 분리** |
| `diff` (신규, 기본값) | 숨겨진 `<textarea>` + 공통 접두사 diff | 아래 참고 |

**기본값이 `diff`로 바뀐다.** 단, 사용자가 예전 체크박스를 **명시적으로 껐던**
경우(`webmanager.terminal.mobileInputWorkaround === '0'`)는 그 의사를 존중해
`native`로 마이그레이션한다 — 즉 그 상태였던 기기는 설정에서 한 번 바꿔줘야 한다.

### 2. `diff` 모드의 핵심 아이디어

지금까지의 모든 설계는 **입력 필드를 매 키 입력마다 잘라냈다**(ANCHOR 리셋). 그래서
키보드가 이미 확정한 문장을 다시 흘려보내면 그게 항상 "새 텍스트"로 보였다 — 그게
중복의 정체다.

`diff` 모드는 반대로 **필드를 자르지 않고 쌓아둔다.** `sent`(이미 PTY로 보낸 문자열)와
현재 값의 **공통 접두사**를 구해서, 줄어든 만큼 `\x7f`, 늘어난 만큼 새 텍스트만 보낸다.

- 키보드가 `가나다`를 다시 흘려보내도 값이 `가나다` 그대로면 diff가 0 → **아무것도 안 보냄**
- 조합은 `<textarea>`에서 정상적으로 일어난다(단일행 `<input>`은 안드로이드에서 입력
  타입이 달라 `compositionstart`가 아예 안 떴다 — 2026-09-03 실측) → **한글도 안 깨짐**
- 백스페이스는 필드에 내용이 있으니 그냥 동작한다(ANCHOR가 있던 이유가 사라짐)

**필드를 리셋하는 시점이 이 설계의 전부다.** 쌓인 값 자체가 중복 방지 장치이므로,
키보드가 아직 그 텍스트를 자기 것으로 여기는 동안 지우면 버그가 그대로 돌아온다.
그래서 **idle 타이머는 일부러 두지 않았고**, 리셋은 세 지점에서만 한다:

- **Enter** — 줄이 끝났으므로 다음 줄의 diff에 끌고 갈 이유가 없다
- **blur** — 사용자가 관찰한 "바깥 탭했다 돌아오면 잠시 정상"을 우연에 맡기지 않고
  명시적으로 재현한 것. IME 세션이 포커스와 함께 끝나는 지점이다
- **길이 상한(512자)** — 위 둘 중 아무것도 안 걸리는 경우의 안전장치

추가로 `\n`이 input 이벤트로 들어오는 키보드(Enter를 keydown으로 안 주는 경우)를
위해 `\n` → `\r` 변환 + 리셋을 넣었다.

### 3. 입력 디버그 오버레이

`research/mobile-ime-hangul-plan.md`의 1단계(계측 먼저). 설정 패널의
"입력 디버그 표시" 체크박스(`webmanager.terminal.inputDebug`)를 켜면 터미널 우하단에
최근 12개 입력 이벤트가 찍힌다: 이벤트 타입, `isComposing`, 필드 값, **실제로 보낸
바이트**. `native` 모드에서도 xterm 자체 textarea에 붙어서 찍히므로 세 모드를 같은
계측으로 비교할 수 있다. React state가 아니라 DOM 직접 조작 — 매 키 입력마다
리렌더할 이유가 없다.

### 4. 모드 전환이 즉시 적용된다

기존 워크어라운드는 xterm 생성 이펙트(deps `[]`) 안에 있어서 **터미널 탭을 나갔다
들어와야** 적용됐다. 실기기에서 방식을 바꿔가며 시험하는 게 목적인데 그건 못 쓸
루프라, 모바일 입력 경로 전체를 `[inputMode, inputDebugEnabled, sendBytes]`에
키가 걸린 **별도 이펙트**로 분리했다.

### 5. 하단 컨트롤 바 버튼이 더 이상 키보드를 열지 않는다 (사용자 요청 3번)

원인은 확정적이었다: `zoom()`/`sendBytes()`/`armModifier()`가 전부
`focusTerminal()`을 불렀고, 그게 `.focus()`이므로 **키보드를 여는 동작 그 자체**였다.
확대/축소만 하려는데 키보드가 열리던 게 이것.

`focusTerminal()`을 없애고 `keepFocus()`로 대체했다 — **이미 포커스를 가진 경우에만**
다시 포커스한다. 열린 키보드는 유지되고(그게 이 호출이 원래 있던 이유), 닫힌 키보드는
열리지 않는다. 데스크탑에서는 `TerminalControls`의 `preventFocusSteal`이 이미 포커스
이동 자체를 막고 있어서 사실상 차이가 없다.

### 6. 터치 모드 선택: 스크롤 / 마우스 / 선택 (사용자 요청 6번)

모바일에서 **텍스트를 선택할 방법이 아예 없었다** — 네이티브 선택도, OSC 52도.
한 손가락 드래그는 세 가지 일을 해야 하는데 기본값 하나로는 안 되므로 터미널 상단에
3-way 선택기를 뒀다(`webmanager.terminal.touchMode`, 터치 기기에서만 표시).

- `scroll` (기본) — 기존 동작 그대로
- `mouse` — 드래그를 **진짜 마우스 이벤트로 합성**해 `.xterm-screen`에 dispatch.
  마우스 트래킹을 켠 앱(tmux/vim/htop/claude)이 실제 클릭·드래그를 받는다
- `select` — 같은 합성 이벤트에 **`shiftKey: true`**. xterm의 "force selection"
  수식자라, 앱이 마우스 트래킹을 켜고 있어도 텍스트 선택이 된다

즉 `select`는 별도 구현이 아니라 `mouse` + xterm이 이미 아는 수식자 하나다. 휠
합성(`dispatchWheel`)이 이미 쓰던 "판단은 xterm에게 되돌려준다"와 같은 접근.

선택이 생기면 상단에 **복사 버튼**이 나타난다(`term.onSelectionChange` → `hasSelection`).
`navigator.clipboard`는 이 배포(평문 http)에서 못 쓰는 경우가 있어 `execCommand`
폴백을 포함한 공용 헬퍼 `utils/clipboard.ts`로 뺐다 — `CopyButton.tsx`도 이걸 쓰도록
정리했다.

### 7. 터미널 탭에서 상단 바 두 줄 → 한 줄 (사용자 요청 5번)

`.mobile-topbar`(햄버거 + "webmanager")는 터미널 탭에서 통째로 숨기고, 그 햄버거를
`.terminal-topbar` 왼쪽으로 옮겼다(`app-shell-terminal` 클래스 + `onToggleSidebar` prop).
`Terminal.css`의 높이 계산에서 `- 3.6rem`이 사라지는 게 실제 이득이다.

## 브라우저로 실제 측정한 것 (2026-09-06)

데스크탑 Chrome에서 `window.matchMedia`를 패치해 `(pointer: coarse)`가 매치되게 만든
뒤 `diff` 모드 필드를 실제로 만들고, 입력 디버그 오버레이로 확인한 결과:

```
field input ic=false v=" 가"      -> "가"
field input ic=false v=" 가나다"   -> "나다"
field input ic=false v=" 가나다"              ← 재전송, 아무것도 안 보냄
field input ic=false v=" 가나"     -> "\x7f"
```

3번째 줄이 이 설계의 핵심 증거다 — 키보드가 이미 확정한 문자열을 그대로 다시
흘려보내는 상황에서 **바이트가 하나도 안 나간다.** 기존 설계들은 여기서 전부
`가나다`를 한 번 더 보냈다.

**단, 이건 diff 로직이 맞다는 증명이지 삼성 IME가 실제로 이 모양으로 이벤트를
준다는 증명이 아니다.** 실기기에서 오는 이벤트 모양이 다르면(예: 필드를 비우고
다시 채우는 식) 결과도 달라진다 — 그래서 디버그 오버레이가 같이 들어갔다.

또 하나: 디버그 오버레이의 초기 구현은 `JSON.stringify`를 써서 백스페이스(`\x7f`)가
`""`로 보였다 — "아무것도 안 보냄"과 구분이 안 됐다. 제어문자를 `\xNN`으로
이스케이프하는 `debugQuote`로 고쳤다. 위 로그의 4번째 줄이 그 결과다.

# 실기기 1차 결과 (2026-09-06) — 3건 실패, 원인 확정 후 수정

사용자가 갤럭시에서 직접 테스트한 결과. **이 절이 최신 상태다.**

## 1. `diff` 모드가 글자 순서를 뒤집었다 — 원인 확정, 수정함

증상: `claude`를 치면 `edual c`가 나왔다. 화면 변화 순서는 `c` → `l c` →
`al c` → ... 였다.

읽어보면 답이 나온다. `claude`를 뒤집으면 `edualc`다. 즉 **매 글자가 필드의 앞쪽
같은 위치에 삽입되고 있었다.** diff는 정직하게 동작했다 — 공통 접두사가 갈리니
백스페이스를 보내고 나머지를 다시 보냈고, 그 결과가 화면상 "앞에 끼워넣기"로 보인
것이다.

왜 항상 같은 위치인가: 필드가 `width:0; height:0`의 화면 밖 textarea라 **살아있는
캐럿이 없고**, 마지막으로 `setSelectionRange`로 명시한 위치(앵커 바로 뒤, 즉 1)가
계속 유지된다. 매 글자가 거기에 꽂힌다.

수정: 커밋된 변경마다 캐럿을 끝으로 다시 고정한다(`pinCaretToEnd`). 조합 중에는
절대 하지 않는다 — IME가 활성인 상태에서 selection을 건드리면 조합이 취소된다.

## 2. 한글이 여전히 전부 쪼개졌다 — 조합이 이 필드에 안 붙는다

`diff` 모드의 `<textarea>`에도 조합이 안 붙었다. 즉 `research/mobile-ime-hangul-plan.md`가
"가장 유력"으로 꼽았던 `<input>` vs `<textarea>` 차이만으로는 설명이 안 된다.

xterm 자신의 helper textarea에서는 조합이 정상적으로 붙는다(워크어라운드를 끄면
확인됨). 그렇다면 남는 차이는 우리가 **추가로** 붙였던 것들뿐이다:

- `aria-hidden="true"`
- `tabIndex = -1`
- `rows = 1`
- 랜덤 `name`

전부 제거하고 xterm의 helper textarea를 속성 단위로 그대로 흉내내도록 바꿨다
(`class="xterm-helper-textarea"`, `aria-multiline="false"`, `tabIndex = 0`,
autocorrect/autocapitalize/spellcheck off). `password` 모드는 원래 설계대로
`aria-hidden`/`tabIndex=-1`/랜덤 name을 유지한다 — 그쪽은 조합을 **억제하는** 게
목적이라 반대 방향이다.

**이건 아직 가설이다.** 다음 실기기 확인에서도 자모가 쪼개지면, 입력 디버그를 켜고
`compositionstart`가 뜨는지만 봐주면 된다 — 안 뜨면 이 방향(속성 차이)이 틀린
것이고, 그때는 xterm의 textarea를 그대로 재사용하되 xterm의 `CompositionHelper`만
우회하는 쪽으로 가야 한다.

## 3. 스페이스에서 리셋 (사용자 제안)

사용자 제안대로 단어 경계에서 필드를 리셋하도록 추가했다. 안드로이드 키보드의
예측 버퍼는 **단어 단위**라, 스페이스가 곧 "키보드가 손을 뗀 지점"이다. 중복 방지가
실제로 필요한 구간(지금 치고 있는 단어 안)은 그대로 보호하면서 필드가 한 줄
전체를 들고 있지 않게 된다.

## 4. 컨트롤 바가 여전히 키보드를 열었다 — 원인 확정, 수정함

`document.activeElement !== target`만으로는 부족했다. **안드로이드에서 뒤로가기로
키보드를 내려도 필드는 포커스를 유지한다.** 그래서 가드를 통과하고 `.focus()`가
불렸다.

`visualViewport` 기반 `useKeyboardInset`이 이미 있으니 그걸 쓴다 — inset이 0이면
아무것도 하지 않는다. 폰에서는 "키보드 닫힘"이고, 데스크탑에서는 inset이 항상 0인데
어차피 이미 포커스된 요소에 `.focus()`를 다시 부르는 건 no-op이었다.

## 5. 선택 모드가 엉뚱한 곳부터 선택됐다 — 원인 확정, 수정함

xterm의 mousedown 핸들러가 이렇다:

```js
this._enabled && e.shiftKey ? this._handleIncrementalClick(e) : this._handleSingleClick(e)
_handleIncrementalClick(e) { this._model.selectionStart && (this._model.selectionEnd = ...) }
```

**`shiftKey`는 "새 선택 시작"이 아니라 "기존 앵커에서 확장"이다.** 앵커를 새로
잡는 건 shift 없는 경로뿐이다. 원래 설계가 `select` 모드에 항상 shift를 실었으니,
두 번째 드래그부터는 이전 선택 위치에서 확장됐다 — 증상 그대로다.

수정:

- shift는 **마우스 리포팅을 뚫어야 할 때만** 싣는다(`sendsScrollToApp(term)`).
  일반 셸에서는 shift 없이 → `_handleSingleClick`이 터치한 지점에 앵커를 잡는다.
- 드래그 시작 전에 `term.clearSelection()` — 새 드래그가 이전 앵커를 물려받지 않게.
- 리포팅이 켜진 앱에서는 `_handleIncrementalClick`이 앵커 없이는 아무것도 안 하므로
  `term.selectLines()`로 **터치한 행**에 앵커를 심어준다. 그 경우 선택은 정확한
  열이 아니라 그 행의 시작에서 시작한다 — 임의 앵커를 잡는 공개 API가 없다.

## 6. "선택하려 하면 최하단으로 스크롤" — 원인 확정, 수정함

xterm은 드래그가 화면 요소 밖에 있으면 `_dragScrollAmount`로 자동 스크롤을 건다.
터치는 손가락이 아래 경계를 넘는 순간 이게 폭주한다. 합성 좌표를 `.xterm-screen`
사각형 안으로 클램프해서 그 타이머가 아예 안 걸리게 했다.

## 7. 관성 스크롤 (신규 요청)

놓는 순간 속도로 계속 스크롤되다 감속한다(Termux 방식). 설정에서 끄고 켤 수 있고
(`webmanager.terminal.touchMomentum`, 기본 켬), 다시 터치하면 그 자리에서 멈추고,
스크롤백 끝에 닿으면 남은 속도를 흘리지 않고 즉시 멈춘다.

**대체 화면 버퍼/마우스 리포팅 경로에는 일부러 관성을 붙이지 않았다** — 그쪽은
스크롤 한 칸이 앱에 들어가는 실제 키 입력이라, 손을 뗀 뒤에도 방향키가 수십 번 더
들어가면 안 된다.

브라우저로 검증하지 못했다: 자동화 탭이 `document.hidden`이라 `requestAnimationFrame`이
아예 돌지 않고, 그 세션에서 창 크기까지 213x186으로 줄어들어 터미널 높이가 0이
됐다. `rAF`를 `setTimeout`으로 갈아끼워 우회하는 것까지는 했지만 창 크기 문제로
결론을 못 냈다 — **실기기 확인 필요.**

## 8. 탭바 가로 스크롤 (사용자가 원한다고 답함)

`.terminal-tab-list`가 줄바꿈 대신 가로 스크롤한다. 스크롤 컨테이너를
`.terminal-tabbar`가 아니라 탭 목록 쪽에 둔 게 요점이다 — 줌 그룹이 스크롤되는
박스 **바깥**의 형제라서 `position: sticky`도, 불투명 배경도, z-index도 필요 없다.
스크롤바는 숨겼다(가로 스크롤바가 이 변경으로 아끼려는 높이를 도로 먹는다).
활성 탭이 화면 밖이면 `scrollIntoView({inline:'nearest'})`로 끌어온다 — 특히
`?session=`으로 복원했을 때 사용자가 스스로 스크롤한 적이 없는 상황이라 필요하다.
