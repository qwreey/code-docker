**8번 원인 정정 (2026-09-04, 사용자 제보).** 커밋 `173d176`의 메시지와 그 전 보고에서

"되던 첫 번째"는 홈 탭이 아니라 **순서상 첫 번째 세션 탭**이었다. 세션 탭은 전부
동일하게 `draggable`이므로 그걸로는 첫 세션 탭만 되는 비대칭이 설명되지 않는다.

맞는 설명은 **활성 탭이냐 아니냐**다. 첫 세션 탭은 대개 이미 활성 상태라 연필을 눌러도
탭 전환이 일어나지 않는다. 반면 두 번째 이후 탭은 먼저 선택돼야 하고, 그 선택이
WS 재연결 캐스케이드(`term.reset()` + `setState('connecting')`)를 부르며 그 과정의
`focusTerminal()`이 방금 `autoFocus`로 들어간 포커스를 터미널로 도로 가져간다.
포커스가 애초에 안 들어가니 blur도 안 나서 닫히지도 않는다 — 증상 전체가 맞는다.

그래서 실제로 고친 것은 `autoFocus`를 `ref` + `useLayoutEffect`(키: `editing?.name`)의
명시적 `.focus()`/`.select()`로 바꾼 부분이고, 이건 캐스케이드가 끝난 뒤에도 다시
실행되므로 포커스가 확정적으로 들어간다. 같이 넣은 `draggable={!isEditing}`은 원인이
아니었고 방어적 하드닝으로 남는다(중첩 `<input>`을 가진 `draggable` 조상은 여전히
피하는 편이 낫다).

커밋 `173d176`의 메시지에는 옛 설명이 남아 있다(푸시 전이라 재작성은 가능하지만

## 1. 프로세스 테이블 정렬이 깨짐 (열/행 둘 다)

**원인 확정.** `.process-flex-table`(`Processes.css:80-154`)가 `<tr>`/`<tbody>`를
`display:flex`로 바꿔서 행마다 CSS `order`(`ProcessTable.tsx:256`, `rankByPid` 기반)로
DOM 이동 없이 시각적 재정렬을 한다 — 스크롤 점프 버그를 고친 커밋 `a40f363`의 장치.
`order`는 flex item에만 먹으므로 표의 네이티브 열 너비 계산이 죽고, **모든 열 너비가
헤더/본문 양쪽에 똑같이 적힌 명시적 `flex-basis`(`.pf-col-*`)에서만 나온다.**

그런데 그 명시적 클래스가 두 파일에 손으로 중복 선언돼 있다:
- 헤더: `ProcessTable.tsx:18-31`의 `COLUMNS`
- 본문: `ProcessRow.tsx:58-80`의 `ProcessRowCells` (별도 파일에 문자열 재선언)
- `cmd`/`actions` 열은 `COLUMNS`에 아예 없고 양쪽에서 각각 하드코딩
  (`ProcessTable.tsx:247-250` vs `ProcessRow.tsx:81-86`)

이미 실제로 어긋나 있다: 커밋 `e5deb7b`이 본문 `<td>`에만 `table-actions-col`
(`common.css:202`, `width:1%`)를 붙이고 헤더 `<th>`에는 안 붙였다. `.pf-col-actions`의
`flex: 0 0 10.5rem`이 이겨서 아직 안 보일 뿐, 헤더/본문 규칙이 갈라진 상태다.
CSS 파일 자신의 주석(80-92행)이 정확히 이 사고를 경고하고 있다.

**수정**: 열 메타데이터(라벨/키/너비)를 **한 배열로 뽑아 두 곳이 import**하게 한다.
`cmd`/`actions`도 그 배열에 넣는다. 이게 최소·안전 수정이다.
`display:flex`를 걷어내고 `table-layout:fixed` + `colgroup`으로 가는 큰 수술은
`order` 기반 재정렬(=`a40f363`의 스크롤 안정성)을 다른 수단으로 대체해야 해서
이번 배치에서는 하지 않는다.

y축 어긋남은 행 높이가 셀 내용(액션 버튼 vs 순수 텍스트)에 따라 달라지는 것이 유력.
행에 고정 높이 + `align-items:center`를 주고 실측 확인.

## 3. "곧 만료" 표현 + 슬립 후 토큰 갱신 실패

**전제 정정이 필요하다.** webmanager에는 **Claude 자격증명 만료 시각을 읽거나 그리는
코드가 아예 없다.** `Auth` 구조체(`internal/claudecode/claudecode.go:75-80`)는
`LoggedIn`/`Email`/`SubscriptionType`/`AuthMethod`뿐이고 `expiresAt` 파싱이 없다.
앱 전체에서 "곧 만료" 문자열은 `SidebarFooter.tsx:31` **하나**뿐인데, 그건
webmanager 자체 authgate 잠금 해제 TTL 카운트다운(`unlockedUntil`)이고 Claude 토큰과
무관하다. → **사용자에게 어느 화면에서 봤는지 확인 필요.** authgate TTL이라면 그 표현은
맞는 표현이라 고칠 게 아니다.

**반면 "슬립 후 안 고쳐진다"는 실재하는 버그이고 원인이 잡혔다:**

- `api/client.ts`의 `request()`(80-135행)가 `AbortController`/타임아웃 **없이** 생 `fetch`
- `ClaudeCode.tsx`의 `load()`(573-593행)는 `loadingRef.current` 가드(574행)로 시작하는데,
  슬립을 가로질러 영영 settle 안 되는 fetch가 하나 걸리면 `finally`에 도달을 못 해
  **`loadingRef.current`가 영구히 `true`**. 이후 "새로고침" 클릭이 전부 조용한 no-op이
  된다 → 사용자가 말한 "창 리프레시하면 괜찮아짐"과 정확히 일치(전체 리로드가 그 JS
  상태를 버림)
- `load()`는 성공 시에만 `setStatus()`를 하고 실패 시 이전 상태를 유지 → 슬립 전
  로그인 상태 카드가 그대로 남고 재로그인 유도가 안 뜬다
- 백엔드도 구분을 안 한다: `handlers_claude.go:55-57`이 CLI 실패/타임아웃(5s,
  `claudecode.go:25`)/파싱 실패/진짜 만료를 **전부 `resp.Auth = nil`로 뭉갠다.**
  프론트의 `auth?.loggedIn` 체크(`ClaudeCode.tsx:453`)는 `null`을 "로그아웃 상태"와
  똑같이 취급 → "만료됐으니 재로그인"과 "조회 자체가 실패"가 구분 불가

**수정** (4개, 순서대로):
1. `api/client.ts`에 `AbortController` + 타임아웃 도입 (전역 개선, 다른 탭도 같이 이득)
2. `ClaudeCode.tsx`의 `load()`를 `try/finally`로 감싸 `loadingRef`를 무조건 해제
3. 백엔드에 오류 구분 추가 — `resp.AuthError`(또는 `Auth.Status` enum)로
   "확인 실패"와 "미로그인/만료"를 나눔
4. 프론트에 오류 상태 UI + 만료 시 재로그인 CTA

## 6. 터미널 cwd를 code로 열기 (좌클릭 = 현재 탭, 중클릭 = 새 탭)

cwd는 이미 추적 중 — `GET /api/terminal/sessions`가 `/proc/<pid>/cwd` 기반 cwd를 주고
3초마다 폴링(`Terminal.tsx:40,322-332`). 지금은 탭 툴팁(`TerminalTabs.tsx:263`)과
"프로젝트 정보" 버튼(`Terminal.tsx:1221-1224`)에만 쓰이고 **눈에 보이는 cwd 표시가 없다.**

재사용할 기존 메커니즘 (`ProjectTable.tsx:134-138, 248-258`):
```jsx
const effectiveCodeServerUrl = codeServerUrl || window.location.origin
`${effectiveCodeServerUrl}/?folder=${encodeURIComponent(path)}`
<a href={...} target="_top" rel="noopener">
```
**진짜 `<a>`이므로 중클릭/Ctrl+클릭 새 탭은 브라우저 기본동작으로 공짜**,
`target="_top"`이 iframe 탈출까지 해준다. JS 핸들러 불필요.

**수정**: `.terminal-topbar`(`Terminal.tsx:1242-1280`)에 활성 세션 cwd를 위 앵커로 표시.
`codeServerUrl`(`WEBMANAGER_CODE_SERVER_URL`, `config.go:28,190`)은 현재 Projects 스캔
응답으로만 내려오므로, `window.location.origin` 폴백으로 먼저 가고 정확한 오버라이드
반영이 필요하면 `/api/terminal/sessions` 응답에 필드 추가.

1. **포커스 탈취/레이스** — 2번째 탭은 "먼저 선택"이 필요하고(또는 더블클릭으로
   선택+편집 동시), 그 선택이 위 재연결 캐스케이드를 부른다. `autoFocus`가 붙는
   시점과 겹치면 포커스가 xterm으로 끌려가고, 포커스가 애초에 안 들어오니
   blur도 안 나서 "닫히지도 않는다"까지 설명된다
2. **오버레이가 탭바를 덮음** — `.terminal-disconnect-overlay`
   (`Terminal.css:234-242`, `Terminal.tsx:1305-1314`)가 `connecting` 동안 떠 있고
   탭바 위를 덮으면 "입력창을 클릭조차 못 한다"가 정확히 설명된다.
   1번만으로는 이 증상이 설명이 안 되므로 **이쪽이 더 유력**

**확인 방법**: 재현 상태에서 DevTools로 (a) `document.activeElement`,
(b) 그 좌표의 `document.elementFromPoint`가 입력창인지 오버레이인지,
(c) `.terminal-tab-rename-input`의 computed `pointer-events`/`z-index`.

**수정 방향**: 오버레이의 `z-index`/영역을 터미널 본문으로 한정 + `autoFocus`를
`ref` + `useLayoutEffect`(키: `editing?.name`)의 명시적 `.focus()`/`.select()`로 교체.

## 9. 프로젝트 다이얼로그에서 잠금 해제가 두 번 뜸

**원인 확정.** 한 Sheet 안에서 서로 모르는 게이팅 두 개가 동시에 발동한다:

1. `ProjectTerminalSessions.tsx` — 기본 `open`(39행), 마운트 즉시
   `api.get('/terminal/sessions')`(60-65행)를 `RequiresUnlock` 래핑 **없이** 호출.
   백엔드가 `gate.RequirePassword`(`main.go:382`)라 401 → `api/client.ts:107-125`의
   전역 인터셉터가 공용 `unlockPrompter` **모달**을 띄움 (프롬프트 1)
2. `ProjectSessionHistory.tsx` — 역시 기본 `open`(36행), 안의 `SessionLog.tsx`가
   자체 `<RequiresUnlock>`(47-61행)으로 `/auth/status`를 선제 확인해 **인라인**
   "잠금 해제 필요" 카드를 그림 (프롬프트 2)

`RequiresUnlock`은 `requestUnlock()`을 부르지 않아서, `api/client.ts:22-31` 주석이
말하는 dedup(수동 `requestUnlock()` ↔ 401 유발 프롬프트)에 참여하지 못한다.
그 dedup은 **401끼리만** 커버한다.

**수정**: 다이얼로그를 **여는 동작 자체**를 한 번 게이팅한다.
`setDetailsPath(...)`(`ProjectTable.tsx:108`) / `openProject`(`App.tsx:161`) 앞에서

`requestUnlock()`(`api/client.ts:28-31`, `SidebarFooter.tsx:47`이 이미 사용)을 await하고,
취소하면 열지 않는다. 통과하면 공용 쿠키가 두 경로를 동시에 만족시키므로
하위 컴포넌트는 손댈 필요 없다.

## 10. `CS_DISABLE_PROXY` — **사용자 전제가 틀렸다**

`--disable-proxy` / `CS_DISABLE_PROXY`는 **없어지지 않았고 지금도 동작한다.**
사용자가 본 `ryanbrainard/code-server`는 2023-07-18에 만들어져 2023-08-07이 마지막
푸시인 포크로, 현재 `coder/code-server:main`보다 **676 커밋 뒤처져 있다**(GitHub compare
API `"status":"behind","behind_by":676`). `--disable-proxy`는 **v4.16.0(2023-07-28)**에
추가됐다 — 저 포크가 죽은 직후라 애초에 들어간 적이 없는 것이지 삭제된 게 아니다.

이 레포가 실제로 설치해 돌리는 바이너리(`installed-version` = **4.109.2**)에서도
end-to-end로 확인:
`out/node/cli.js:136-138,199,232-234,478-479`(옵션 정의 + env 파싱),
`out/node/http.js:63-65`(`proxyEnabled = (req) => !req.args["disable-proxy"]`),
`out/node/routes/pathProxy.js:60-62,86-90`, `out/node/routes/domainProxy.js:47`,
`out/node/main.js:202-203`(기동 시 `"Proxy disabled"` 로그).

**단, 사용자가 관측한 현상은 실재하고 진짜 구멍이 맞다.** code-server 자신의
`docs/FAQ.md`가 명시한다: 이 옵션은 **포워딩된 포트로 가는 프록시 라우트만** 막고,
**VS Code 워크벤치의 자동 포트 포워딩 자체는 안 막는다**. PORTS 탭과 알림은 계속 뜬다
(실제로 열어보면 `/proxy/`에서 막히긴 함). 그래서 upstream FAQ는
`remote.autoForwardPorts`를 `false`로 같이 두라고 권한다.

**code-docker는 `remote.autoForwardPorts`를 어디에도 설정하지 않는다**
(`autoForwardPorts`/`remote.autoForward` grep 0건). 그리고 애초에 **기본
`settings.json`을 심는 메커니즘이 없다** — `config/code/code-config.default.yaml`은
code-server CLI 옵션 파일이라 워크벤치 설정 키를 담을 수 없다.

**수정**:
1. `settings.json` 시딩 메커니즘 신설 — `config/code/settings.default.json`
   (+ `.override.json`), `code-service.default.sh:9-16`이 config.yaml을 쓰는 것과 같은
   자리에서 `/code/.local/share/code-docker/code/user-data/User/settings.json`에 시딩.
   **사용자가 편집한 파일을 덮어쓰면 안 되므로, `code-patch.default.sh`의 해시 매니페스트
   방식(`.code-patch-manifest`)을 그대로 차용한다** — 라이브 파일 해시가 마지막으로
   심은 값과 같을 때만 갱신
2. 기본값에 `remote.autoForwardPorts: false`(+ 검토 후 `remote.restoreForwardedPorts: false`)
3. 문서 정정 — 루트 `CLAUDE.md:71`, `docs/build-customization.md:65`, `example-env:225-227`에
   "이 옵션은 프록시 라우트만 막고 PORTS 탭 UI는 안 막는다, 그래서 설정 쪽도 같이 본다"를 추가.
   **기존 서술이 틀린 건 아니므로 삭제가 아니라 보강**

주의: 메모리의 "code-server settings.json은 강제하지 않는다" 판단이 있으므로,
시딩 대상은 **꼭 필요한 키만** 담고 사용자 편집을 존중하는 위 해시 방식이 전제다.

## 12. 사이드바 "곧 만료"가 영원히 안 바뀜 (3번 항목의 정체)

**원인 확정.** 3번에서 "어느 화면인지 확인 필요"라고 했던 게 이것 — 사이드바 하단이
맞고, Claude 토큰과는 무관한 webmanager authgate 잠금 표시다.

**TTL은 없어지지 않았다**: `internal/authgate/gate.go:45,53` — `sessionTTL = 10분`
(sliding idle) + `maxSessionLifetime = 12시간`(하드 캡). 게이트를 통과하는 요청이 있고
절반(`refreshThreshold`, 5분) 넘게 지났으면 `refreshCookie`(gate.go:326)가 쿠키를 민다.

**깨진 건 표시 쪽이다**: `SidebarFooter.tsx`의 `useTicker(30_000)`은 30초마다
**리렌더만** 건다. 데이터를 다시 안 받는다 — `useAuthStatus()`
(`components/common/useAuthStatus.ts`)는 마운트 1회 + `onAuthStatusChange` 이벤트에만
`/auth/status`를 호출한다. 그래서 잠금 해제 시점의 `unlockedUntil` 스냅샷 하나를 잡고
그 **고정된 과거 값**으로 `formatRemaining`을 반복 계산 → 10분 뒤 `ms <= 0`이 되어
`'곧 만료'`(`SidebarFooter.tsx:33`)에 도달하면 **영구히 거기 고정**된다.
그동안 실제 세션은 다른 API 호출들이 계속 밀어줘서 멀쩡히 열려 있다.

**수정**: ticker가 리렌더 대신 `refresh()`를 부르게 한다.
`GET /api/auth/status`는 `main.go:338`에서 `RequirePassword` 래핑 **없이** 등록돼 있어
폴링해도 쿠키가 밀리지 않는다 — 즉 30초 폴링이 idle 타임아웃을 무력화하지 않는다.
(이게 이 수정의 전제이고, 확인함.)
