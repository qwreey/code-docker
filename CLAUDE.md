# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal Arch Linux-based Docker image bundling `code-server` (browser VS Code), `sshd`, `mise` (runtime version manager), a Docker-in-Docker sidecar, and a `router` boundary container, orchestrated by `supervisord`. There is no application source code, test suite, or linter here — this is infrastructure/config (Dockerfile, shell scripts, YAML).

Five external projects are pulled in as tag-pinned remote references (Docker/Compose remote-git build contexts or includes), not git submodules: `code-server-autoinstall` (`AUTOINSTALL_REF`), `router-docker` (`ROUTER_REF`), `dind-authz-docker` (`DIND_REF`), `router-docker-client` (`ROUTER_CLIENT_REF` - netshare, dns-local, netinit-docker), and the `envmigrate` Go module. A change in one of them reaches a deployment only through a new tag plus a bump of the default here, then `docker compose build` and `up -d` (`up -d` alone never rebuilds an existing image). `router-docker-client` is also pinned by every `builds/` sibling and by dind-authz-docker, each in its own Dockerfile; `./dev-bump-router-client.sh vX.Y.Z` rewrites all of those pins at once (`--commit` to commit each repo). A Compose remote *include* (router) must name a tag or branch; a commit sha fails and leaves a broken cache directory. For local development, `./dev-clone.sh` checks each of these out under `dev/<name>` and prints the `.env` lines (`ROUTER_INCLUDE`, `DIND_CONTEXT`, `AUTOINSTALL_SOURCE`, `ROUTER_CLIENT_SOURCE`) that point the build at the local checkout instead of the remote ref. A second, unrelated directory, `builds/<name>`, holds sibling *provider* projects (code-docker-chrome, roblox-studio-docker, ...) that attach to the running stack via `EXTRA_INCLUDE` — see "Development checkout layout" below for the distinction.

## Commands

```sh
docker compose build   # rebuild the image after Dockerfile/config/script changes
docker compose up -d   # (re)start
docker compose build code-docker && docker compose up -d   # after editing a config/*.override.* file
```

There are no automated tests or linters in this repo. Validate changes by building the image and, when practical, exercising the affected service through `docker compose up` (e.g. checking `docker compose logs`, opening the code-server URL, `ssh`-ing in).

If a repo-root `.allow-test` file exists (gitignored — `touch .allow-test` to create it), the running `docker compose` stack in this checkout is a disposable test environment, not someone's live/in-use instance — building, restarting, and exercising services freely (without asking first) is fine. Without it, treat the stack as potentially live and confirm before rebuilding/restarting.

## Architecture

### The override pattern

Nearly every runtime behavior is defined by a pair of files under `config/`: `<name>.default.*` (checked into git) and an optional `<name>.override.*` (gitignored, user-provided). The choice is made in exactly one place, `script/override` (installed as `/etc/code-docker/override`): `override exec code/code-service.default.sh` runs `code/code-service.override.sh` if it exists, else the default; `override path <rel>` prints the chosen path for things that are read rather than run (`nginx.default.conf`, `supervisord.default.conf`, `shell/shell.default`). Every supervisord program's `command=`, the entrypoint, the build step, and `code-service.default.sh`'s own sub-steps call it. Adding a new customizable behavior means adding a `<name>.default.*` file and calling it through `override`, not writing another if/else.

`config/` has one subfolder per program: `build/`, `code/` (code-server itself — `code-patch/`, `settings.default.json`, `recommendations.default.yaml`), `dns-local/`, `git/hooks/`, `nginx/`, `shell/`, `sshd/`, `user-init/`, `vector/`, `webmanager/`. `supervisord.default.conf`, `supervisord.d/*.conf`, and `supervisor-metadata.default.yaml` stay directly under `config/` — cross-cutting infra, not owned by any one program. The root Dockerfile `COPY`s the whole `config/` tree in one shot, so this layout carries straight through to `/etc/code-docker/...` with no per-folder Dockerfile wiring.

`.sh` override files must be `chmod u+x`. Editing an override requires a rebuild (`docker compose build && up`), not just a container restart.

### Process model

`entrypoint.sh` waits for `code-docker-netinit-docker` to plant a default route (see "Network topology"), bootstraps DNS via `apply_nameserver` (skippable with `NETGATE_ENABLED=false`), runs `user-init.sh` synchronously, then `exec`s `supervisord`.

- `user-init.default.sh` runs once per boot, **before** supervisord starts (so no program can race it touching `$HOME`), `set -e` (a failed migration kills the container loudly rather than continuing half-migrated). It tracks a version in `/code/.local/share/code-docker/migration-version` and only re-runs first-time setup (fish shell config, qwreey-fish) once — a future migration step gets added gated on `[ "$OLD_VERSION" -lt N ]`. It also unconditionally `mkdir -p`s `/code/Projects` every boot (no DE/browser here to run `xdg-user-dirs`, but webmanager's Projects tab scans that path).
- `code-service.default.sh` delegates to `code-server-autoinstall`'s `start.sh` via `code-runner.default.sh`, which first does `mise env --shell bash` so mise-installed tools are on `PATH` for the service, not just interactive shells. `code-runner.default.sh` always appends `--bind-addr=$CODE_SERVER_BIND_ADDR` as a CLI arg (default `127.0.0.1:8080`), which wins over anything in `code-config.default.yaml`/`.override.yaml` — so an override can't silently re-expose code-server past loopback. The `private` network alias this used to default to is gone; using it now fails loudly.
- `sshd-service.default.sh` inits `/etc/ssh` from `/etc/default/ssh` (baked in at build time) on first run, then execs `sshd -D`.

supervisord's config (`config/supervisord.default.conf`) has three `[include]` globs: `config/supervisord.d/*.conf` (git-tracked, one `[program:...]` per file — code, dns-local, sshd, webmanager, nginx, vector), `config/supervisord/*.conf` (gitignored, a user's own runtime addition), and `/code/.local/share/code-docker/supervisord/*.conf` on the `/code` volume — the only one that gains a program *without a rebuild* (what makes a `mise`-installed tool usable as a managed service, and what lets a side project run something *inside* code-docker without this repo knowing its name). `entrypoint.sh` `mkdir -p`s that third path and each on-volume unit's log directory before `exec`ing supervisord, since supervisord refuses to start at all if a configured logfile's parent directory is missing. `bin/restart` (`supervisorctl restart code`, backgrounded via `setsid` since it's issued from the terminal it's about to kill) is how a user picks up `mise`-installed toolchain or patch edits without a rebuild; `bin/reload-services` (`supervisorctl reread && update`) is how a newly dropped on-volume unit gets started.

Every program's stdout/stderr is captured to a rotated file at `/var/log/<program>/{stdout,stderr}.log` (`%(program_name)s` in every `[program:X]` block), not `/dev/fd/1` directly. `vector` (`config/vector/vector.default.toml`, the one program still on raw stdout — `priority=1` so it starts first and stops *last*, since it needs to keep tailing everyone else while they shut down) tails every `stdout.log*`/`stderr.log*`, tags each line with `app_name` from the path, and re-emits a `[app_name] message` copy to its own stdout — that's what makes `docker compose logs` readable. It also writes structured JSON-lines to `/code/.local/share/code-docker/vector/logs/<date>.jsonl`, which webmanager's Logs page reads directly (`webmanager/backend/internal/logstore`, no vector API involved).

### Development checkout layout (`builds/` vs `dev/`)

`./dev-clone.sh` (repo root, host-side like `ootb.sh`) clones the repos code-docker is developed together with into this checkout, as independent git repos under two gitignored directories; re-running it fast-forward-pulls each and reports why when it can't (uncommitted changes, no upstream, diverged). It never edits `.env`/`extra-include.yml`, only prints the lines to add.

- `builds/<name>` — sibling providers that join the stack through `EXTRA_INCLUDE` (code-docker-chrome, roblox-studio-docker, code-docker-trilium, code-docker-firecrawl). Same path `ootb-extra.sh` clones into on a real deployment, so a dev `extra-include.yml` matches one written by ootb byte-for-byte.
- `dev/<name>` — local checkouts of the four core dependencies described in "What this is" (`router-docker-client`, `router-docker`, `dind-authz-docker`, `code-server-autoinstall`), bound via `ROUTER_CLIENT_SOURCE`/`ROUTER_INCLUDE`/`DIND_CONTEXT`/`AUTOINSTALL_SOURCE`. `envmigrate` is an ordinary Go module instead, swapped in via an uncommitted `go.work` (`dev-clone.sh` prints the exact `go work init` commands) rather than an env var.

The two are kept apart because the scripts treat them differently: `migrate-continue.sh` re-applies every `builds/*/ootb-manifest.env` listed in `EXTRA_INCLUDE`; nothing reads `dev/` except the build-context variables a user points at it.

### Network topology

Two user-defined networks: `code-docker-internal` (`internal: true`, no outside route) and `code-docker-external` (has internet/host access). `code-docker` and `code-docker-dind` are attached to `code-docker-internal` only — neither has an interface with a route to the internet of its own. `code-docker-router` is the only container on both networks, and is the sole egress/ingress chokepoint. All service/network names are prefixed with `${PREFIX:-}` so multiple instances can coexist on one host.

A container gets its default route from outside its own netns, planted by the `code-docker-netinit-docker` service (`network_mode: host`, `NET_ADMIN`+`SYS_ADMIN`, docker.sock-mounted — root-on-host-equivalent already from the socket mount alone, `:ro` notwithstanding, since read-only restricts the inode, not what may be written over the socket). Opt-in is entirely label-driven, fail-closed (an unlabelled container is never touched):
- A **network** label `netinit.provider` names the agent, `netinit.gateway` names a container (never a raw IP — accepting one would let a compose line hand a workload a route to RFC1918) whose IP becomes the default route for anything on that network, and `netinit.exempt-forward: "true"` installs a `DOCKER-USER` exemption (needed because Docker Engine 29.x's hardening otherwise drops router's own FORWARD traffic to an `internal: true` network at the host netfilter level, before router's own iptables ever sees it).
- A **workload** container opts in with its own `netinit.provider` label. A container attached to two gateway-declaring networks is refused with a loud error rather than guessed at.

`code-docker-dind` does not use this agent — being `privileged: true` already, it plants its own default route and `/etc/resolv.conf` from inside itself (`netshare`'s `apply_default_route`/`apply_nameserver`), synchronously before `dockerd` starts (`dockerd` snapshots `/etc/resolv.conf` at its own startup, so doing this in the background could lose that race), then keeps a background loop for upkeep.

Because the route is planted from *outside* a container after it starts, every opted-in client has to wait for it before starting its real workload. `script/entrypoint.sh` does this via `NETINIT_WAIT`/`NETINIT_WAIT_TIMEOUT` (defaulting to whatever `NETGATE_ENABLED` says, so the one documented opt-out keeps working). `NETGATE_ENABLED` (default `true`) is a **behavioral** opt-out only — it skips `entrypoint.sh`'s DNS bootstrap, dind's own loop, and maps onto `code-docker-netinit-docker`'s `NETINIT_DOCKER_ENABLED` (its `DOCKER-USER` exemption half stays on regardless) — it does **not** undo the compose topology (`code-docker-external` isn't re-attached by a runtime env var).

**Always address `code-docker-dind` via the `dind` alias** (a `code-docker-internal`-scoped network alias), never the bare service name — it becomes ambiguous again the moment `code-docker-external` is manually restored on either service. Use it for `DOCKER_HOST` and for reaching any port published by a container created inside dind; such containers live in the inner daemon's own private network and are not reachable by name on `code-docker-internal` otherwise.

See `.claude/archive/netinit-docker-plan-done.md` and `.claude/archive/egress-netgate-plan-done.md` for the design history and incidents behind these rules; `dev/router-docker/docs/egress-netgate.md` for the `DOCKER-USER`/netgate mechanism.

### router / dind / webmanager — the contract

**router** (`router-docker`, pulled in as a remote Compose include pinned to `ROUTER_REF`) owns everything about code-docker's network boundary: netgate (egress lockdown), tailscale, Dev Proxy/App Routes, tinyauth, vhosts, VNC, and its own `router-manager` admin backend + SPA at `/router/`. Its own `docker-compose.router.yml` defines the `code-docker-router` service; this repo's `docker-compose.yml` only merges in `env_file: .env.router` and the `ROUTER_VOLUME` bind mount, whose relative paths must resolve against *this* file's location, not router-docker's. `ROUTER_HOSTNAME` (default `router`) must match the alias on `code-docker-router`'s own `networks:` block — both `entrypoint.sh` and dind's routing loop resolve it. router's own feature env vars live in `.env.router` (template fetched by `ootb.sh`'s `fetch_router_env_template`, since `example-env.router` is no longer a file in this checkout); `ALLOWED_HOSTS`/`TRUSTED_PROXIES`/`NGINX_LOG_LEVEL` are genuinely shared with code-docker's own nginx and stay in this repo's `example-env`. router's front door (tcp 80) is externally reachable only — see the security section below. Everything else about router's internals belongs in `dev/router-docker/CLAUDE.md` (after `./dev-clone.sh`), not here.

**dind** (`dind-authz-docker`, remote build context pinned to `DIND_REF`, `target: dind-authz` by default) layers an authorization plugin denying privileged/host-escalation container creation on top of plain `docker:dind`, and binds the daemon only to its `code-docker-internal` IP instead of `0.0.0.0:2375`. It runs `privileged: true` with an unauthenticated, TLS-less socket — see the security section. Its own `CLAUDE.md` (`dev/dind-authz-docker/CLAUDE.md`) covers the authz plugin design; this repo only needs the compose wiring above and the `dind` alias rule.

**webmanager** (`webmanager/`, its own subtree with its own `CLAUDE.md`/`plan.md`) is a Go backend + Vite/React frontend running as another supervisord program. In-container nginx (`config/nginx/nginx.default.conf`) puts code-server and webmanager on one origin: `/` proxies to code-server (`CODE_SERVER_BIND_ADDR`, default `127.0.0.1:8080`), `/manager/` proxies to webmanager (`WEBMANAGER_ADDR`, default `127.0.0.1:81`) — both bind loopback-only now, nginx is the only thing listening beyond it. webmanager trusts `X-Real-IP` only from a loopback peer (nginx overwrites it on every proxied location; `authgate.ClientKey` keys the password-lockout on this), and wraps every route in `net/http`'s `CrossOriginProtection` (refuses a non-GET/HEAD/OPTIONS request a browser marks cross-origin) as CSRF defense, since webmanager has no login of its own by default. It covers process management, SSH keys, git config (incl. the AI commit-trailer rewrite, see "git hooks" below), the vector-backed Logs page, a Projects browser (git status/worktrees/session history), Claude Code session/memory viewers, code-server extension and mise tool management, Docker/dind management, PWA manifest shortcuts, a web terminal, a full file manager, and a File share tab (WebDAV — see the security section). Dev Proxy and VNC tabs are a same-page `<iframe>` embed of router's own `/router/` page, calling router's front door directly from the browser — not proxied through code-docker's nginx at all (router-manager never calls back into webmanager or vice versa server-side). An opt-in shared password gate (`internal/authgate`, off by default, `WEBMANAGER_AUTH_PASSWORD_HASH`) protects Terminal/File Manager/Logs/Sessions/File-share entirely and gates write actions elsewhere; it does not cover Dev Proxy or Tailscale, which are router-manager's own API gated by its own separate `internal/authgate` instance.

### code-server: patch, settings, extension

`config/code/code-patch/` seeds `<name>.default.<ext>`(+ optional `.override.<ext>`) into `/code/.local/share/code-docker/code/patch/<name>.<ext>`; code-server-autoinstall auto-injects every top-level `patch/*.js` as a `<script>` tag on every start. Re-seeded every boot, but **only when the live target's content still hashes to what was seeded last time** (`.code-patch-manifest` tracks `<name>\t<hash>` pairs) — so a bundled fix reaches an already-running container, but a user's direct edit is left alone. A file with no recorded hash (predates hash-tracking, or user-edited) is never touched; deleting the seeded file once forces a fresh hash-tracked reseed.

`config/code/settings.default.json` seeds code-server's **user** `settings.json` (via `code-settings.default.sh`, after `install.sh`, before code-server starts) — **create-only**, not the hash-refresh scheme above, because `settings.json` belongs to the user/VS Code (rewritten on every settings-UI toggle) and is JSONC, so there's no safe shell-side merge. When the file already exists, the script prints which bundled keys therefore didn't apply, rather than skipping silently. Adding a key here is a deliberate security decision, not routine (the one shipped, `remote.autoForwardPorts: false`, is the other half of `CS_DISABLE_PROXY` below).

`config/code/code-extensions.default.sh` keeps the built-in webmanager extension (`webmanager/vscode-extension/`) installed at exactly the image's build — **always re-synced**, compared by a build stamp (hash of extension source) so a rebuild always lands and an Extensions-view uninstall is undone on next start. `CODE_WEBMANAGER_EXTENSION=false` is the only off switch.

### ootb.sh / migrate.sh

`ootb.sh` is first-install only (never touches an existing `.env*`); `migrate.sh` is existing-deployment only, and `exec`s `migrate-continue.sh` after `git pull` so a fix that just landed applies in the same run. Both share `ootb-lib.sh`.

Interactive `.env`/`.env.router` values are asked in exactly one place, `ootb-config.sh` — `ootb.sh` runs it plainly, `migrate-continue.sh` runs it with `RECONFIGURE=1` — so a new prompt reaches both fresh installs and existing deployments at once. A sibling project attaches by carrying its own `ootb-manifest.env`; reading and applying it lives in exactly one place, `ootb-lib.sh`'s `load_manifest` + `apply_manifest_declarative`, called from both `ootb-extra.sh` and `migrate-continue.sh`'s step 3 — a new declarative field goes into `apply_manifest_declarative` to reach both paths at once. See `docs/tips/ootb-manifest.md` for the manifest schema.

### git hooks

`config/git/hooks/` holds a global git hook set the image points `core.hooksPath` at. The Dockerfile symlinks **every** git hook name (not just the ones implemented) to `hook-dispatch`, because a global `core.hooksPath` *replaces* a repository's own `.git/hooks/` for every hook name, not just the ones present — shipping only our own would silently kill husky/pre-commit/lefthook/etc. in every project in the container. `hook-dispatch` runs the repository's own hook first (resolved via `git rev-parse --absolute-git-dir`, **not** `--git-path hooks/<name>`, which honors `core.hooksPath` and recurses forever), then our own `<name>.default.sh`/`.override.sh` if one exists, `exec`ing when only one side exists so stdin-reading hooks pass it through untouched.

The one behavior implemented, `ai-trailer.sh`, rewrites the `Co-Authored-By: Claude ... <noreply@anthropic.com>` trailer into a user-chosen identity, matched on **email domain**, never display name. Default-off (`codedocker.aitrailer.enabled`) — with no name/email configured, the documented fallback to `user.name`/`user.email` would rewrite the co-author into the commit's own author. It runs from **both** `prepare-commit-msg` (before the editor — misses a trailer typed during `git rebase -i`'s reword, since the sequencer fires it on the *old* message) and `commit-msg` (after the editor, but skipped by `--no-verify`) — safe to run twice since the rewrite is idempotent.

## Security-relevant, intentional trade-offs

- `code-config.default.yaml` sets `auth: none` — code-server has no login; a reverse proxy with forward-auth is expected in front of it. Because of that, code-server's own port-proxy routes (`/proxy/<port>/`, `/absproxy/<port>/`) are disabled by default (`CS_DISABLE_PROXY`, defaulted in `code-server-autoinstall`'s `start.sh`, passed through from `.env`) — they'd proxy to *any* port listening in the container. This gates the proxy *routes* only, not the PORTS tab's auto-detection/notifications, which is why `remote.autoForwardPorts: false` is also shipped as a default editor setting.
- code-server and webmanager both bind loopback-only (`127.0.0.1:8080`/`127.0.0.1:81`); in-container nginx is the only thing listening beyond it, on one origin (`/` and `/manager/`). webmanager trusts `X-Real-IP` only from a loopback peer and wraps every route in CSRF protection (`net/http`'s `CrossOriginProtection`) since it has no login by default.
- `code-docker-netinit-docker` mounts `docker.sock` `:ro` plus `NET_ADMIN`/`SYS_ADMIN` to `nsenter` into other containers' netns (mounted `:ro,rslave` — `rslave` is mandatory: with default `rprivate` propagation, a container created after this service starts shows up as an empty 0-byte handle and `nsenter` fails). `:ro` on the socket is not a mitigation — it restricts the inode, not what may be written over the socket, and still serves container-create calls — so this service is root-on-host-equivalent regardless of the extra caps.
- `code-docker-dind` runs `privileged: true` with an unauthenticated, TLS-less daemon socket (`DOCKER_TLS_CERTDIR: ""`), reachable only from `code-docker-internal` — but anyone who can reach that network gets host-kernel-equivalent access via it.
- router's front door (tcp 80 — everything code-server/webmanager/App Routes/Dev Proxy/vhosts sit behind) accepts connections only on its outward-facing interface and loopback (`ROUTER_FRONTDOOR_EXTERNAL_ONLY`, router-docker v0.1.1+). Without this, router's nginx listened on every network it's a gateway on, so an isolated sibling project's network had a way back into code-server/webmanager through it.
- `cap_add: SYS_PTRACE` (debuggers like gdb/btop) and `IPC_LOCK` (IDE/LSP IPC) are added to code-docker by default.
- webmanager's File share tab (`internal/webdavshare`) exposes `WEBMANAGER_WEBDAV_ROOT` over WebDAV behind a **separate** password from `WEBMANAGER_AUTH_PASSWORD_HASH` — forced, not stylistic: WebDAV clients speak Basic auth and can't follow an SSO redirect, so the route must be excluded from the outer forward-auth, at which point its own password is the only guard on a read/write view of the home volume. Off by default, fail-closed (no password → 404, touches no filesystem), argon2id with a 5-minute success cache (a WebDAV client re-sends Basic auth on every request; paying full argon2id per PROPFIND would be self-DoSing). Meant to be exposed via a dedicated hostname (`NGINX_WEBDAV_PORT`, default 82, 404 for everything but `/webdav`) rather than a path, since a vhost upstream is a bare `host[:port]` with no path. See `docs/tips/webdav.md`.
- Containers created *inside* `code-docker-dind` live in the inner daemon's own private network — not reachable by name on `code-docker-internal`; reach them via `dind:<published-port>`. Inherent to nested Docker-in-Docker; not "fixed" via a host-socket mount, since that would remove the one isolation layer the nested daemon provides.

## Documentation map

- **`README.md`** — a short intro only (screenshot, one paragraph, pointer into `docs/`). Never add setup/feature content here.
- **`docs/*.md`** (+ `docs/tips/*.md`) — user-facing documentation: setup, the override system from a user's perspective, per-integration tips. Add a new customizable file or environment trick to `docs/index.md` or the relevant page here, in the existing style.
- **`CLAUDE.md`** (this file) — the current architecture and rules an agent needs, for this repo only. A sibling or external repo's own internals (router-docker, dind-authz-docker, webmanager's own subsystems) are documented in that repo/subtree, not duplicated here — link to it instead.
- **`.claude/backlog/*.md`** — not-yet-started ideas/plans.
- **`.claude/archive/*-done.md`** — finished work: the design/rationale, the incident that prompted it, how it was found. This is where history, dates, commit hashes, and "verified on..." belong — not in comments or in this file.

**Comment and doc style, enforced when editing any of the above:**
- State *why the code is the way it is now*. When something changed, and how it was found, goes in the commit message and `.claude/archive/`, not the comment.
- Explain a fact in exactly one place — the one nearest the code or env var that owns it. Everywhere else links to it.
- Split a paragraph once it runs past ~500 characters; prefer bullets.
- A sibling or external repo's internals are documented in that repo. Here, only the contract with it.
